API 일치도 스코어보드

고정된 공개 저장소의 API 명세와 코드 분석 결과를 비교한 재현율과 일치도입니다.

실제 저장소에 포함된 OpenAPI 계약과 코드 분석 결과를 소스만 읽어 비교합니다. 테스트 픽스처를 정답으로 사용하지 않습니다. 코퍼스는 저장소 15개와 기술 10개로 구성됩니다. 확인 가능한 계약을 기준으로 선택했으므로 이 수치를 그 프레임워크의 모든 프로젝트에 일반화할 수 없습니다. 아래 표의 기술 식별자와 저장소 메타데이터는 원문을 유지합니다.

측정 방법

scripts/scoreboard/corpus.json에는 저장소 커밋, 코드 기술, 서비스 범위, 선택한 OpenAPI 파일, 선택적 spec_prefix와 exclude_paths, 짧은 설명만 저장합니다. 제외 경로는 Noir의 기존 --exclude-path 옵션으로 전달하는 명시적인 서비스 경계이며 스냅샷 식별자에도 포함됩니다. NodeBB의 별도 웹 설치 서버(install/web.js:63-68)와 Gotify의 예제 플러그인(plugin/example/echo/echo.go:74-77)은 평가하는 서비스 밖이므로 제외합니다. 실행기는 고정된 커밋을 얕게 가져와 그 서비스와 선택한 명세 파일을 임시 공간에 내보냅니다. 다른 OpenAPI 진입 문서는 제거합니다. 평가 대상 분석기의 경로 소스가 아닌 WebAssembly(*.wasm)와 CSV 데이터셋(*.csv)은 제외합니다. 스캔 오류가 있으면 게시용 파일 생성을 중단합니다. 코퍼스 애플리케이션은 빌드하거나 설치하거나 실행하지 않습니다.

한 번의 Noir 스캔에서 코드와 OpenAPI를 함께 읽습니다. 최적화된 HTTP 행의 details.technologies에 평가 대상 코드 기술과 spec 기여자가 함께 있으면 matched, 코드 기여자만 없으면 spec-only, 명세 기여자만 없으면 code-only입니다. 단일 기여자는 details.technology에서 읽습니다. 기술별 비율은 저장소별 개수를 합산한 뒤 계산합니다.

  • Recall(재현율) = matched / (matched + spec-only). 문서의 HTTP 동작 중 코드 분석기가 찾은 비율입니다.
  • Agreement(일치도) = matched / (matched + code-only). 코드 출력 중 명세에도 있는 비율입니다. 일치한 명세 동작이 유효하다는 전제에서 정밀도의 하한이며, 측정된 정밀도는 아닙니다. 실제로 존재하지만 문서화되지 않은 health, admin, UI 경로도 이 값을 낮춥니다.
  • **Marked(표시된 행)**는 비어 있지 않은 resolution 맵이 있는 코드 엔드포인트를 한 번씩 셉니다. 각 claim:status도 같은 코드 분모로 별도 집계하므로 서로 겹칠 수 있습니다. 표시가 없다고 정확성을 보장하지 않습니다. 선택적 AI 컨텍스트와 태거는 활성화하지 않습니다.
  • 분모가 0이면 결과는 null, 표는 n/a입니다. 파라미터, 스키마, 인증, WebSocket, 실제 실행 시 접근 가능성은 평가하지 않습니다. Noir가 가져오지 못하는 명세 동작은 분모에 포함되지 않습니다.

명시적인 배포 접두사 보정

Supabase Auth는 spec_prefix: "/auth/v1"을 선언합니다. openapi.yaml:37-38은 호스팅 서버 URL을 https://{project}.supabase.co/auth/v1로 지정합니다. 서비스는 로컬 경로를 등록합니다. internal/api/api.go:219-222는 / 라우터를 열고 :268은 /token을 등록합니다. internal/api/router.go:17-31은 경로를 그대로 chi에 넘깁니다. API는 이 라우터에 직접 전달하고(api.go:498,520), cmd/serve_cmd.go:63-75는 /auth/v1 마운트 없이 API를 HTTP 서버 핸들러로 설치합니다. 따라서 이 접두사는 소스에서 누락된 경로가 아닌 호스팅 배포 경계입니다.

실행기는 이 명세를 가져오기 전에 임시 복사본의 루트 서버 URL에서 명시된 접두사만 제거합니다. 그러면 Noir가 자체 병합을 하기 전에 명세 행이 로컬 경로가 됩니다. 선언된 모든 서버 경로가 설정한 접두사와 정확히 같은지 검사하며 경로·동작별 서버 재정의가 있으면 거부합니다. 원본 체크아웃과 코드 행은 바꾸지 않고 별도 엔드포인트 매처도 추가하지 않습니다. 보정한 명세의 행 번호는 임시 복사본을 가리키며, 코드 위치는 고정된 원본 소스를 가리킵니다.

Flowable은 프로세스 컨트롤러 라이브러리에 spec_prefix: "/flowable-rest/service"를 선언합니다. 커밋된 Swagger 2 문서의 20행이 이 basePath를 지정합니다. 별도 REST 애플리케이션은 modules/flowable-app-rest/src/main/resources/flowable-default.properties:2에서 /flowable-rest 컨텍스트를, 43행에서 /service 서블릿 경로를 설정합니다. Spring Boot 자동 구성 모듈의 BaseRestApiConfiguration.java:41-48은 이 서블릿 매핑을 설치합니다. 배포 설정은 스캔 범위인 modules/flowable-rest/src/main 라이브러리 밖에 있으며, 직접 작성한 컨트롤러는 로컬 경로를 등록합니다(예: DeploymentCollectionResource.java:106). 실행기는 Swagger 2의 basePath가 정확히 일치하는지 확인하고 임시 복사본의 값만 /로 바꿉니다. 동작 경로는 바꾸지 않습니다.

Owncast는 다릅니다. webserver/router/router.go:93은 생성된 API를 /api/에 마운트합니다. 명세의 /api는 소스에도 있으므로 유지합니다. Supabase Auth와 Flowable에만 접두사 보정이 있습니다. 파라미터 표기는 Noir 자체 정규화를 사용하며 대소문자, 끝 슬래시, ANY, 와일드카드, 상수 접두사, 게이트웨이 재작성 매칭을 추가하지 않습니다. 게이트웨이 규칙은 API 동작과 일대일로 대응하지 않아 제외합니다.

소스 감사

아래 날짜가 있는 표는 측정 스냅샷에 대한 수동 감사입니다. 초기 감사는 기술별로 불일치 행을 최대 25개씩 확인했습니다. 저장소와 spec-only/code-only 조합에 표본 수를 배분하고 정렬된 목록에서 일정 간격으로 선택합니다. 전체 오류 추정치가 아닌 표본 개수이며, 같은 동작이 양쪽 불일치에 포함될 수 있습니다.

분류는 분석기 누락, 분석기 오탐, 오래되거나 잘못된 명세, 문서화되지 않은 경로, 분석기 오류가 아닌 접두사·메서드·끝 슬래시 차이, 기타입니다. 분류는 비율을 바꾸지 않습니다. 행별 근거는 커밋하지 않습니다. 새 측정을 게시하기 전에 바뀐 행을 다시 확인하고 이 날짜가 있는 표를 갱신해야 합니다. 레시피는 측정값만 생성하며 수동 감사를 재생성하지 않습니다.

이 감사는 분석기 리비전 8184cd4에서 했습니다. 여기서 찾은 누락 중 두 가지는 그 뒤 고쳐졌습니다. FastAPI 행의 누락 25건은 모두 InvokeAI의 /api 접두사 손실(#3614)이었고, go_chi의 누락은 supabase/auth의 SCIM 접두사(#3616)였습니다. FastAPI에 남은 불일치 4건은 다시 감사하지 않았습니다. 나머지 끝 슬래시 차이는 보정하지 않습니다. Express 불일치 11개 행은 모두 감사했습니다.

확장 감사: 2026-11-15, 분석기 리비전 54ff7225277f691ac19816faad875c52979e39c0. 새로 고정한 저장소 5개의 불일치 행 137개를 추가로 소스와 대조했습니다. langflow 행은 2026-11-16에 830b4cfce775d24812f4b0305df6fc24359dcdcb에서 다시 감사했습니다. 각 저장소의 양쪽을 별도로 표본 추출합니다. 한쪽이 25개 이하면 전부, 더 많으면 정렬된 목록에서 floor(i * count / 25) 위치의 25개를 확인합니다. 위의 과거 표는 유지하며 기존 코퍼스를 현재 리비전으로 다시 감사했다는 뜻이 아닙니다. 기존 저장소 10개의 모든 측정값 필드는 커밋된 기준 결과와 같습니다.

Flowable의 기타 3건은 명세의 리터럴 users 동작 2개와 표본에 든 {family} 컨트롤러 행 1개입니다. ProcessInstanceIdentityLinkResource.java:49,73,98-100은 경로를 등록하고 users 또는 groups인지 확인합니다. 리터럴과 파라미터의 특수화 차이입니다. 나머지 표본 동작은 실제 등록되어 있지만 계약에는 없습니다. Gotify 표본은 UI·문서, 명시적인 HEAD health, 조건부 MCP 경로입니다. Pretalx 표본은 REST 계약 밖의 주최자·일정·발표 제출 UI 경로입니다.

NodeBB는 라우트 모듈마다 마운트 이름을 인자로 넘깁니다. src/routes/index.js:236-254는 기본값이 admin, user, tags 등인 플러그인 훅에서 이름을 받고, src/routes/admin.js 같은 모듈은 경로를 /${name}/...로 만듭니다. 명세는 기본 이름으로 적혀 있고 Noir는 /api/{name}/...와 /{name}/...를 출력하므로, 같은 라우트가 불일치 양쪽에 한 번씩 나타납니다. 표본의 누락 23건과 오탐 16건이 이 원인입니다. 추가 오탐 1건은 index.js:136의 미들웨어 전용 router.all 정규식입니다. src/middleware/index.js:130-133은 next()만 호출합니다. 오래된 명세 1건은 삭제된 읽기 API의 세션 삭제 경로이며, 대체 경로는 src/routes/write/users.js:66에 등록되어 있습니다. 접두사 차이 1건은 /ping으로, 소스가 설정 가능한 relative_path를 앞에 붙입니다(src/webserver.js:152,191).

Langflow는 처음에 명세의 84개 동작 중 4개만 일치했습니다. 패키지 __init__.py에서 다시 내보낸 라우터가 /api/v1과 /api/v2를 잃었기 때문입니다(#3625). 이를 고친 뒤에는 84개가 모두 일치합니다. 표본으로 본 코드 전용 25행 중 24행은 프로젝트가 include_in_schema=False로 명세에서 숨긴 라우트입니다. 라우터에 지정한 경우(api/v1/deployments.py:36, models.py:24, knowledge_bases.py:35)와 라우트에 지정한 경우가 있습니다. 나머지 1행은 main.py:584의 정적 파일 마운트입니다.

다시 실행하기와 산출물

just scoreboard
bash docs/scripts/check_doc_parity.sh
hwaro build -i docs

레시피는 필요할 때 실행하며 컴파일 게이트를 거치는 build-release에 의존합니다. git, tar, 캐시에 없는 커밋을 가져올 네트워크가 필요합니다. 체크아웃과 복사본은 $TMPDIR/noir-codex-scoreboard/에 보관합니다. TMPDIR이 없으면 /tmp/noir-codex-scoreboard/를 사용합니다. 저장소별 matched/spec-only/code-only 목록과 기술별 감사 표본은 git에서 제외된 tmp/scoreboard/에 작성하며 커밋하지 않습니다.

작은 회귀 비교 스냅샷인 scripts/scoreboard/results.json에는 개수, 비율, 표시 개수, 저장소 커밋, 날짜, 분석기 리비전이 있습니다. 분석기 리비전과 코퍼스가 같으면 스냅샷 날짜를 유지합니다. 실행 전에 분석기와 의존성 변경을 커밋해야 합니다. 수정되거나 추적되지 않은 src 파일과 변경된 shard 매니페스트가 있으면 거부합니다. 출력은 정렬하며 실행 시간과 절대 임시 경로를 넣지 않습니다.

Hwaro는 커밋된 마크다운 표를 렌더링하고 빌드 시 결과 JSON을 읽지 않습니다. 따라서 결과 파일은 docs/data/ 대신 코퍼스와 함께 보관합니다. CI의 지원 기술 문서 생성기는 이 레시피를 호출하거나 코퍼스를 가져오지 않습니다. 사이트는 오프라인으로 빌드할 수 있습니다.

선택하지 않은 후보

  • spring-petclinic-rest: 메서드 매핑은 빌드 시 명세에서 생성하며 체크아웃에 없습니다. 그래서 0%가 나와도 분석기 실패가 아닙니다.
  • juice-shop: 명세는 B2B 주문만 다룹니다. 서비스 전체를 평가하면 일치도가 주로 명세의 좁은 범위를 반영합니다.
  • 이전 Spring 대체 후보: 초기 조사에서 spring-cloud-dataflow, ThingsBoard, Stirling-PDF에는 적합한 커밋된 계약이 없었습니다. 이번 확장에는 동작 15개의 Flowable decision 계약 대신 동작 184개의 process 서비스 Swagger 2 계약을 넣었습니다. OpenAPI 3 대안은 계속 제외합니다. docs/public-api/references/openapi/README.md:5-7이 불완전하다고 명시합니다. 안정된 Swagger 문서는 소스 주석에서 생성한 뒤 수동으로 보정한다고 references/swagger/README.md:7-13에 설명하며, 생성기의 tools/flowable-oas-generator/pom.xml:51-84가 프로세스 컨트롤러 패키지를 지정합니다.
  • 두 번째 Express 후보: Directus의 계약은 넓은 범위를 다루지만 현재 Access, Policies, Panels, Notifications, Deployment API가 없고 오래된 OAuth·관계 경로가 남아 있습니다. 추가하지 않았으며 이번에 NodeBB를 두 번째 Express 데이터 포인트로 넣었습니다. RealWorld Express 앱에는 커밋된 OpenAPI 문서가 없었습니다.
  • OWASP/crAPI: 공유 명세가 여러 서비스에 걸쳐 있어 한 코드 기술의 별도 분모로 쓸 수 없습니다.
  • spring-petclinic-microservices: 확인한 커밋에 OpenAPI 문서가 없습니다.
  • VAmPI: 독립적인 Flask 선언 대신 같은 명세로 Connexion이 경로를 생성합니다.
  • shlink: 코퍼스가 이미 충분한 기술을 다뤄서 넣지 않았습니다. 명세가 오래됐기 때문은 아닙니다.

이번 확장에서 확인했지만 넣지 않은 후보는 다음과 같습니다. apache/fineract(Spring 매핑이 아닌 JAX-RS @Path 리소스), novuhq/novu(내보내기가 API 키 인증 없는 엔드포인트를 제거), thomiceli/opengist(문서가 토큰 API만 다루고 라우트와 대조하는 검사가 없음), dyrector-io/dyrectorio(Swagger 설정만 커밋되어 있고 생성된 문서는 없음), 그리고 PrefectHQ/prefect, freqtrade/freqtrade, healthchecks/healthchecks, PostHog/posthog, wger-project/wger, statping-ng/statping-ng(커밋된 서비스 OpenAPI 문서 없음)입니다. Langflow는 스키마 생성기를 도입한 커밋에 고정했습니다. 현재 head에서는 워크플로 라우트가 스캔 범위 밖의 별도 lfx 패키지에서 옵니다. 이 커밋은 점수를 보기 전에 골랐으며, 현재 Langflow를 측정한 결과는 아닙니다.
